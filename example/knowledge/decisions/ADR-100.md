title: Modules own their data and communicate through interfaces
status: active

## Decision

Each module owns its own tables. No module reads another module's storage
directly; all cross-module access goes through the owning module's interface.

## Why

Regeneration works at module scope. If `orders` reads `customer` tables
directly, regenerating `customer` can silently break `orders` in a way no
contract on either module would catch, because the coupling is invisible to
both knowledge packages.

## Alternatives considered

- **Shared database with foreign keys.** Rejected: convenient, but it makes the
  regeneration scope unknowable, which defeats the point.

## Consequences

- The address copy captured on an order (BR-010) is a consequence of this rule,
  not merely a business preference.
- Cross-module rules must declare `affects` for every module involved, so impact
  analysis can find them.
